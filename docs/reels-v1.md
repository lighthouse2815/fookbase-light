# Reels V1

Reels are specialized `Posts` in the same ASP.NET Core monolith and the same
`FookbaseDbContext`. `Posts.PostType` is `Standard` or `Reel`; the migration
defaults every existing post to `Standard`. A Reel always uses a Profile
container and has exactly one `PostMedia` video. Group Reels are not supported.

## APIs

- `POST /api/reels` creates an authenticated Reel from one owned, processed,
  ready video. Caption is optional; privacy uses the existing `public`,
  `friends`, and `onlyMe` values.
- `GET /api/reels/{id}` applies normal Post privacy and block rules. Public
  metadata can be read anonymously, while playable media requires a JWT.
- `GET /api/reels?cursor=&limit=` is the authenticated, deterministic
  `CreatedAtUtc DESC, Id DESC` browsing feed. It includes own Reels, visible
  friend Reels, and public discovery Reels; Home Feed V2 remains Standard-only.
- `GET /api/reels/{id}/video/access` and `/poster/access` check access before
  issuing signed Cloudinary URLs for playback and poster display.
- `POST /api/reels/{id}/views` stores one bounded meaningful watch signal. It
  requires an authenticated viewer and rejects zero, negative, or
  longer-than-video durations.

Existing `/api/posts/{id}/reaction`, comments, comment reactions, reports and
notifications operate on Reel post IDs without parallel Reel interaction
tables or notification types.

## Video lifecycle

Images retain `PendingUpload -> Ready`. A validated MP4/WebM video follows:

`PendingUpload -> Processing -> Ready`

After HTTP completion validates Cloudinary metadata and the initial file signature, it
only stores a durable `MediaProcessingJobs` row; it never runs FFmpeg in the
request. The BackgroundService claims jobs, downloads to a generated temporary
directory, retries bounded failures and records a generic user-safe failure.
After the final failed attempt it marks the asset `Failed` and queues cleanup.
The job and its fixed derivative keys make a restart safe: a retry overwrites
the same private output keys, and a persisted successful job is never claimed
again.

`MediaAsset` stores `DurationMs`, `Width`, `Height`, processed/poster private
object keys and processing timestamps. A Reel can only reference a Ready video
with all of that metadata, within configured duration limits. Processing error
details remain internal; normal media metadata only exposes status.

## FFmpeg strategy

The production image installs `ffmpeg` and `ffprobe` before switching to the
non-root `fookbase` user. Arguments are supplied with `ProcessStartInfo`
`ArgumentList`, never a user-derived shell command. Input/output paths and
object keys are generated by the server.

`ffprobe` selects the first video stream and reads duration, dimensions, codec
and container JSON. `ffmpeg` produces one browser-compatible private MP4:

```text
ffmpeg -i input -map 0:v:0 -map 0:a? -c:v libx264 -preset veryfast -crf 23 \
  -pix_fmt yuv420p -c:a aac -b:a 128k -movflags +faststart \
  -vf scale=w='min(1280,iw)':h=-2:force_original_aspect_ratio=decrease processed.mp4
```

It then generates a JPEG poster from the normalized file. The scale only
reduces oversized sources and preserves aspect ratio; V1 intentionally has no
HLS or multi-bitrate output. Each FFmpeg/FFprobe process has a configured
timeout and is killed as a process tree on timeout.

## Storage and deletion

Originals, processed MP4s and posters use authenticated Cloudinary delivery. A
live Reel creates a normal `MediaReference`, so `DELETE /api/media/{id}` is
conflict-protected until the Reel is deleted. Deleting an unreferenced processed
video appends durable `ObjectDeletions` rows for original, normalized video and
poster; the existing deletion worker performs eventual idempotent cleanup.

## Deferred

V1 does not implement HLS, CDN delivery, ML ranking, creator analytics,
share/save, Stories, Pages, live streaming or a distributed SignalR backplane.
